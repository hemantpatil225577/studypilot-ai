# StudyPilot AI

Next.js (App Router, TypeScript) + Supabase (Auth, Postgres, RLS) + a configurable LLM provider.
Students manage a syllabus, get an AI or rules-based study plan, chat with a tutor, take server-graded quizzes, and see analytics computed from saved data.

## Status (read this first)

This code was written in a sandbox with **no network access**. `npm install`, `next build`, `tsc`, `eslint`, Supabase and the AI provider were **never run**.
The only executed verification: the pure-logic tests in `tests/logic.test.ts` (24 cases covering schedule validation, rules planner, revision engine, grading, analytics, JSON extraction) passed under Node's test runner using a small vitest shim. They have not yet run under real Vitest.

## Setup

1. `npm install`
2. Create a Supabase project. In the SQL editor run `supabase/migrations/0001_init.sql`.
3. Supabase > Authentication > URL configuration: add `http://localhost:3000/auth/callback` (and your Vercel URL) as redirect URLs. For fastest local testing you may disable "Confirm email".
4. `cp .env.example .env.local` and fill in the Supabase URL, anon key, service-role key, and the AI settings.
5. `npm run dev`

### AI provider
Set `AI_PROVIDER` (`anthropic` or `openai`), `AI_API_KEY`, and `AI_MODEL` (a model your key can use). Any OpenAI-compatible endpoint works with `AI_PROVIDER=openai` and `AI_BASE_URL`.
If the key is missing or the call fails, the planner and quiz routes return an explicit error and offer a **clearly labelled** rules-based plan or sample quiz. Fallback output is stored with `source = rules / sample` and shown with that label in the UI.

### Deploy to Vercel
Import the repo, add every variable from `.env.example` (service-role key and AI key as server-only), set `NEXT_PUBLIC_SITE_URL` to the production URL, deploy, then add that URL to Supabase redirect URLs.

## Architecture
- `src/middleware.ts` refreshes the session and redirects unauthenticated users; each API route and server action re-checks the user.
- `src/app/api/{plan,tutor,quiz}` are validated (Zod) route handlers wrapped by `route()` for central error handling.
- `src/lib/ai/provider.ts` is the provider abstraction (timeout, no provider internals leaked).
- Pure logic with unit tests: `planner.ts` (schedule validation + rules planner), `revision.ts`, `grading.ts`, `analytics.ts`.
- Server actions in `src/app/actions.ts` handle CRUD with ownership filters.

## Security decisions
- RLS on every table. Topics can only reference the owner's subjects.
- Quiz tables are read-only for users. The `correct_index` and `explanation` columns are not granted to the browser role. The service role writes quizzes/attempts and reads answer keys only after the route verified the quiz belongs to the user. Scores are computed on the server.
- Mastery changes from quizzes and completed sessions are computed server-side. Users can still edit their own mastery manually in Subjects (the spec asks for this).
- AI plans are rejected (not saved) if they contain unknown topic IDs, invalid or out-of-window dates, duplicates, overlaps, or exceed the daily limit.
- Topic titles and questions are wrapped in `<data>` tags with an instruction not to follow them (prompt-injection hardening; reduces, not eliminates, the risk).
- Security headers in `next.config.mjs`. Logs contain event names only.

## Revision engine
Score = 0.4 × weakness + 0.3 × exam urgency + 0.15 × difficulty + 0.15 × quiz-accuracy gap. Reasons are shown beside each recommendation. It is a rules engine, not machine learning. Mastery after a quiz = 0.6 × old + 0.4 × score%; +5 per completed session. These constants are heuristics, not tuned values.

## Known limitations
- Not built or run yet (see Status). No Playwright end-to-end tests are included.
- Not implemented: PDF/text upload (omitted rather than faked), light theme, streaming tutor replies (responses arrive whole).
- Rate limiting is in-memory per server instance; use a shared store (e.g. Redis) for strict limits on serverless.
- "Today" on the server uses UTC; the planner window uses the date the browser sends.
- UI primitives are hand-written in shadcn style, not generated by the shadcn CLI.
- The planner uses one daily start time in the rules planner (18:00); the AI picks times itself.
- `check:rls` needs two real test accounts in your own project; it has not been run.
